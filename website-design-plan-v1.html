Engineering Control Plane · Product Website

把控制平面讲清楚，而不是把 Skill 列出来

这是 rd-skills 官网的整体设计与实施方案。核心判断只有一条：官网的差异化不在“我们有很多 Skill”，而在“一次任务如何被边界、专业归属、证据和独立 Review 约束着走完”。因此全站的结构、数据源和视觉都围绕这条主干组织。

方案摘要

  • 站点形态：Next.js App Router 全静态官网，5 类路由，无账户、无后端、无数据库。
  • 唯一真源：所有 Skill 数据与统计数字由上游仓库 machenjie/rd-skills 的 registry 构建期同步生成，网站不维护第二套 Skill 数据。
  • 叙事主干（已随 V24 改写）：Request → 选专业 → Inspect → Edit → Self-check → Fresh Validation → Report，外加 Analysis 与 Independent Review 两个按需分支。首页每一段只服务这条线上的一个环节。
  • 视觉方向：Developer Infrastructure。图表即插画，终端即演示；禁止机器人、大脑、渐变星空与 AI 插图。
  • 已确认并实现：英文单语官网；submodule 接入上游 registry；上游文档站内可读；/quickstart 为 agent/scope 安装向导；M0–M5 全量交付，209 个静态页面（见 §10、§11）。

01输入核对与冲突裁定

PRD 与 v22 指南在架构模型上高度一致：六平面、四 Agent、三层 Skill、Evidence Ledger、L1–L5、Host Adapter 全部对得上。但有四处会直接写进页面文案的冲突，必须先裁定，否则官网会发布与真实运行时不符的内容——这本身就违反 rd-skills 自己的 Evidence 原则。

C1 Quickstart 命令里的 --profile 已经不存在 Blocking
PRD
§12 给出 quickstart.py --agent codex --scope user --profile recommended 与 installers/doctor.py --profile recommended。
v22
§22 明确：不再让用户选择 recommended / full / dev，安装、upgrade、doctor 都没有 --profile；recommended 仅作为 dist/**/recommended/ 的兼容 identity 保留。
裁定
以上游仓库当前 CLI 为准。Quickstart 页面的命令块不允许手写，必须由同步脚本从仓库 README / docs 抽取并在 CI 中校验；抽取失败则构建失败。发布一条跑不通的安装命令，是这个官网最贵的错误。
C2 “5 Supported Host Families” 会构成过度承诺 诚实性
PRD
§7.3 把 “5 Supported Host Families” 作为首页系统指标之一。
v22
§24 能力矩阵中，Cline 与 OpenAI API 在 Profile / Skill loading / Subagent / Review diff / Validation 五项上均为 unsupported；Codex 与 Claude 的 Review diff 路径也不同（native vs supplied-artifact）。
裁定
首页数字改为 5 Host Adapters，并在 Host 段落直接呈现真实能力矩阵，用 native / prompt / supplied-artifact / unsupported 四态标注。PRD §11 自己也写了“不要宣称所有 Host 功能完全一致”，两处保持一致即可。
C3 Execution Level 的语义标签不能自造 术语
PRD
§10 建议 L1 Bounded / L2 Standard / L3 Elevated / L4 High Assurance / L5 Critical，并注明“具体名字应最终以 Registry / Docs 为准”。
v22
§12 的实际语义是：L1 = strict minimal eligibility，L2 = bounded / reversible，L3 = 默认标准可执行 Task，L4 = 存在可达的 material residual risk，L5 = extra assurance materially useful。
裁定
采用 v22 语义。L3 是默认档而不是“提升档”，这个差别会直接改变读者对整套体系的理解。页面用 Assurance Ladder 呈现，并显式标注“Level 是保证强度，不是执行阶段”。
C4 首页系统指标应该换成更硬的数字 增强
PRD
§7.3 的六个数字偏“模型描述”（4 / 3 / 1 / 0–3 / 5）。
v22
提供了可核验的库存数字：189 source skills、26 runtime top-level、163 Layer 3 source、612 references、154 JIT items。
裁定
两类混合。保留 4 Agent Roles / 0–3 Layer 3 表达模型约束，加入 26 Runtime Skills 与 154 JIT Items 表达真实规模——“顶层只有 26，深度留在后面”本身就是产品主张，比抽象数字更有说服力。
缺口 G1：语言策略未定。 PRD 全部文案为英文，而 v22 指南是中文为主的双语文档。这决定路由是否需要 /zh、文案量是否翻倍、以及 SEO 主战场。见 §11 决策 A。
缺口 G2：本仓库没有 registry。 当前仓库只有 prd-v1.md 与指南 HTML，没有 src/registry/*.yaml。Skill 数据的接入方式必须先定，否则 §3 无法落地。见 §11 决策 B。

03数据架构（唯一真源）

这是整个项目最容易做错、也最难补救的部分。PRD §18 已经明确禁止“Website manually maintained skill database”。下面把它变成可执行的机制。

三级来源优先级

P0Repository Registrysrc/registry/professional-skills.yaml、foundation-skills.yaml、domain registry — 权威来源
P1Generated Marketplace Index构建产物中的 catalog / manifest，用于补齐 registry 未直接暴露的投影信息
P2Committed Snapshotdata/skills.snapshot.json — last-known-good，进版本库。上游不可达时构建仍然成功
硬性约束：网站代码只读取 data/skills.generated.json 一个文件。任何组件里出现手写的 Skill 名称、描述或计数，视为缺陷。首页那六个数字同样从这个文件派生。

同步脚本 scripts/sync-rd-skills.ts

  1. 拉取上游指定 ref（默认 main，可用环境变量覆盖）的 registry 与 catalog 文件。
  2. 规范化为下方 schema，计算派生统计（各类型计数、Layer 3 总数、references 总数、runtime top-level 数）。
  3. Schema 校验 + 完整性断言：slug 唯一、type 合法、每个 Professional 至少有 triggerSignals 与 outputContract、sourcePath 可解析为 GitHub 链接。
  4. 与 snapshot 做 diff，输出变更摘要（新增/移除/描述变更），便于 review。
  5. 写入 data/skills.generated.json，并在成功时更新 snapshot。
  6. 失败时：记录原因 → 回落 snapshot → 构建继续 → 在构建日志与页面 <meta> 中标记数据时间戳。

规范化 schema

type SkillType = "control" | "professional" | "foundation" | "domain";

interface Skill {
  name: string;                 // backend-change-builder
  slug: string;                 // backend-change-builder
  type: SkillType;
  title: string;                // Backend Change Builder
  description: string;          // 一句话：拥有哪类工程决定
  group?: string;               // 需求分析 / 影响判断 / 实现 Owner / Gate / Review
  roleSupport: AgentRole[];     // main | analysis | task | review
  triggerSignals: string[];
  antiTriggerSignals: string[];
  requiredInputs: string[];
  outputContract: string[];
  layer3Candidates: string[];   // slug 引用，构建期校验存在性
  references: { title: string; path: string }[];
  sourcePath: string;           // src/professional-skills/<name>/SKILL.md
  runtimeTopLevel: boolean;     // control | professional = true
}

interface SkillDataset {
  generatedAt: string;          // ISO
  sourceRef: string;            // 上游 commit sha
  degraded: boolean;            // 是否回落 snapshot
  skills: Skill[];
  counts: {
    sourceTotal: number; control: number; professional: number;
    foundation: number; domain: number;
    runtimeTopLevel: number; jitItems: number; references: number;
  };
}

GitHub 动态数据

Star / Fork 数走 ISR（revalidate: 3600），失败即隐藏，不阻塞任何页面。仓库元信息（默认分支、latest release）构建期获取并写入 snapshot。构建绝不能因为 GitHub API 抖动而失败。

五种图示语言（全站复用，不允许一次性图表）

Plane Stack

六平面纵向堆叠，每层左侧色条 + 右侧组件 chip。Hover 某层时其余层降至 40% 不透明度。用于 /architecture 与首页 §7.7。

Role Relay

四个 Agent 卡片 + 连接轨。每张卡必须同时写“能做”和“故意不能做”——后者才是产品主张。

Skill Tree

Control → Primary Professional → selector → 0–3 Layer 3 → References 的收敛树。紫色分支表示 JIT，默认折叠，展开是首页最重要的一次交互。

Evidence Track

Unverified → Validated → Reviewed → Completed 的状态轨。每个状态同时用颜色、形状和文字标注（可访问性硬要求）。

Terminal

等宽面板，带 scope 标题栏。Hero 用它演示任务生命周期，Quickstart 用它承载可复制命令。行高、缩进、颜色语义两处完全一致。

视觉禁令（PRD §16，逐条纳入 PR checklist）：无 AI 机器人 / 大脑 / 宇宙背景 / 霓虹 Cyberpunk / 大面积渐变 / 3D 球体 / 图库照片 / emoji 图标 / AI 生成插图。任何一条出现即 review 打回。

08动效与可访问性

动效准则

  • 动画必须解释系统，不解释就删除。
  • 微交互 150–400ms，缓动统一 cubic-bezier(.2,.8,.2,1)。
  • Hero 生命周期只自动播一次，不循环。
  • 滚动触发用 IntersectionObserver，不用滚动劫持。
  • prefers-reduced-motion 下全部改为终态直出。

可访问性硬指标

  • 状态不得只靠颜色：颜色 + 形状 + 文字三重编码。
  • 明暗双主题均达 WCAG AA。
  • 所有图表提供文本 fallback（<figcaption> 或 sr-only 描述）。
  • Explorer 过滤器、Skill Tree 展开、主题切换全部键盘可达，焦点环可见。
  • 主题切换用无闪烁内联脚本 + data-theme，尊重系统默认。

A语言策略 · 英文单语 已修订

初次决策为「英文界面 + 中文 /guide」，已按后续要求修订：官网本身就是用来替代旧版中文指南的，因此 /guide 路由与 public/guide/ 静态件一并移除，站点为英文单语。

修订后的实施 深度内容改由 /docs 承担：上游 docs/*.md 在构建期渲染为 HTML，站内直接阅读，正文内的相对链接自动改写为站内路由（指向已渲染的文档）或 GitHub blob（指向未渲染的文件）。MARKETPLACE_CATALOG.md（160KB 生成清单）保持外链。

B数据接入 · git submodule

以 submodule 引入 machenjie/rd-skills，构建期直接读取本地 registry 文件，不依赖 GitHub API。

已核实 上游仓库可达，src/registry/ 下有 control / professional / foundation / domain 四份 registry；字段与 §3 的 schema 基本一一对应（trigger_signals、anti_trigger_signals、required_inputs、output_contract、layer3_candidates、reference_index、role_support）。skill 的一句话描述取自各 SKILL.md 的 frontmatter description。目录实测：25 Professional / 13 Domain / 1 Control。当前 submodule 跟踪 master（曾短暂锁定 codex/improve_token_usage_quality，因该分支被 force-push 而改为 master）。

D上手体验 · 安装向导 新增

目标是让普通开发者最快上手，因此 /quickstart 不再只是罗列 README 命令，而是一个向导：选 agent（5 个）与 scope，实时生成可复制的四到五条命令，并显示文件将落在哪个目录、该 host 是否有原生 agent profile。

数据来源 选项与路径全部从安装器源码抽取（SOURCE_SKILL_ROOTS、SOURCE_PROFILE_ROOTS、DEFAULT_SKILL_TARGETS、PROJECT_SKILL_SUBPATHS，以及 quickstart.py 的 AGENTS / SCOPES），因此向导不可能给出 CLI 会拒绝的组合。另加一条断言：README 列出的 host 若不在安装器接受范围内，构建失败。
